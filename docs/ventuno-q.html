Arduino VENTUNO Q

The Arduino VENTUNO Q is built around the Qualcomm QCS8275 (Monaco) SoC, also marketed as Dragonwing IQ-8275, and boots from eMMC. monaco.mk builds its open boot chain from TF-A and OP-TEE, which support Monaco as a SoC of its own next to Lemans, and U-Boot, plus a Linux kernel with a Buildroot initramfs. The quick start goes from an empty directory to a flashed board.

Boot chain

XBL -> TF-A BL2 (tz) -> BL31 -> OP-TEE -> U-Boot (uefi) -> UKI (efi): Linux at EL2

XBL loads TF-A BL2 from the tz partition and the FIP, wrapped in an ELF, from the uefi partition. BL2 loads BL31, OP-TEE (BL32) and U-Boot (BL33) from the FIP. U-Boot starts the UKI from the ESP through UEFI (bootefi bootmgr, which finds it as EFI/BOOT/bootaa64.efi).

The TZ stage: TF-A BL2 or U-Boot SPL

TF-A BL2 is the TZ stage by default. TZ_IMAGE=u-boot-spl makes U-Boot SPL the TZ stage instead, as on the IQ-9075 EVK. Pass the same TZ_IMAGE to bootimage, tz-qti-sign and flash-loader: 

make bootimage TZ_IMAGE=u-boot-spl   # u-boot-spl.elf, uefi.elf
make tz-qti-sign TZ_IMAGE=u-boot-spl     # tz.mbn from u-boot-spl.elf
make flash-loader TZ_IMAGE=u-boot-spl

XBL loads the uefi image to 0xaf000000 before it starts the TZ stage, so SPL needs no storage driver: it finds a FIT with BL31, OP-TEE and U-Boot there (monaco/uefi.its, wrapped and signed like the FIP ELF), loads the three images to the addresses in the table above and starts BL31. TF-A is built as BL31 only.

Unlike on the IQ-9075 EVK, the SPL needs a QTI signature, like BL2: XBL checks the QTI signature of the TZ image even with secure boot disabled (see Signing). SPL has to fit where XBL enters the TZ image, 0x14680000 to 0x1469a000 in system IMEM, with its BSS and stack; it prints its banner on the debug UART XBL leaves set up. SPL needs a U-Boot tree with qcom_monaco_spl_defconfig, which the tree monaco.xml pins does not have yet, and it has not been run on a board yet.

The board device tree (monaco-arduino-monza.dts) is in mainline since v7.1, as is the Monaco EL2 overlay (monaco-el2.dtso). The kernel has no combined EL2 DTB for this board, so monaco.mk builds the board DTB with symbols and applies the overlay with the kernel's fdtoverlay.

The pinned kernel carries patches that are not submitted yet: DSP (PAS) start without a resource table, audio recovery across an ADSP restart, the fixes for booting with maxcpus, and two PCIe fixes for the PI7C9X2G304 switch on PCIe0: L1 PM Substates disabled on the root port link (config reads to the switch could stall a CPU) and the switch's Training Error masked (it made AER reset the TUSB7340 link in a loop).

Boot CPU

XBL and TF-A enter U-Boot on CPU0, a Cortex-A78C. The Cortex-A78C cores have pointer authentication and the Cortex-A55 cores do not, and Linux only brings up CPUs that match its boot CPU in that respect. The board configuration (CONFIG_BOOT0_QCOM_BOOT_CPU) makes U-Boot start the first Cortex-A55 (MPIDR 0x10000) with PSCI CPU_ON and turn CPU0 off, so U-Boot and Linux run on a Cortex-A55 and all eight CPUs come up.

Build

make toolchains
make all                         # bl2.elf, fip.elf, efi.bin in monaco/output/
make tz-qti-sign QTI_SIGN_DIR=... CASS_CAPABILITY=... \
     QTI_SIGN_SERVER_URL=... QTI_SIGN_SERVER_PORT=...   # tz.mbn

tz-qti-sign adds the SWIV segment and signs bl2.elf with Qualcomm sectools through the QTI remote signing service; the Monaco TZ security profile comes from the Qualcomm signing package. Without access to it, put a signed tz.mbn in monaco/input/: flash-loader uses monaco/output/tz.mbn when there is one and monaco/input/tz.mbn otherwise. make bootimage removes monaco/output/tz.mbn, as it no longer matches the new bl2.elf.

Each make invocation stamps a build identifier, BUILD_ID (default monaco-<UTC date-time>), into the TF-A build string, the OP-TEE version, the U-Boot and Linux versions and /etc/issue, and fails the build if an image lacks it. monaco/output/build-info.txt records the identifier of each image, so the console shows which build is running.

Flash

qdl writes the images by partition name; the partition table and everything else on the eMMC stay as they are. Both slots are written, so the boot chain cannot fall back to the stock images. The firehose programmer comes from the board's stock software image and goes in monaco/input/ (or set FIREHOSE); see monaco/input/README.md. 

make flash-loader    # tz_a, tz_b <- tz.mbn; uefi_a, uefi_b <- fip.elf
make flash-kernel    # efi <- efi.bin

which run:

qdl --storage emmc prog_firehose_ddr.elf \
    write tz_a tz.mbn write tz_b tz.mbn \
    write uefi_a fip.elf write uefi_b fip.elf
qdl --storage emmc prog_firehose_ddr.elf write efi efi.bin

DSPs and audio

The rootfs carries the ADSP, CDSP and GPDSP firmware from linux-firmware (qcom/qcs8300), the FastRPC userspace and runtime, and qcom-tests (ADSP and CDSP FastRPC, the GPDSP boot state, CPU stress, and CDSP FastRPC in an unsigned PD). The FastRPC runtime has to come from the DSP build of the firmware, since a DSP only loads the shell and skels whose hashes its signed image carries; the build installs the QCS8300-RIDE runtime of that build under the Arduino Monza path the DT model maps to, and checks the pairing.

The DSPs are started through the OP-TEE PAS service (the Monaco PAS pseudo-TA, embedded as an early TA), which relies on the TF-A Monaco clock setup; monaco.xml pins OP-TEE and TF-A revisions with both.

The sound card, ALSA id arduinomonza (card 1; the loopback card is card 0), runs on the ADSP with the AudioReach topology from linux-firmware. Playback on the headphone output needs the route the upstream UCM profile sets: 

amixer -c arduinomonza cset name='LPI_MI2S_RX_0 Audio Mixer MultiMedia1' on
amixer -c arduinomonza cset name='Headphone Switch' on
aplay -D hw:arduinomonza,0 -f S16_LE -r 48000 -c 2 file.wav
