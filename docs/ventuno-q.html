Arduino VENTUNO Q

The Arduino VENTUNO Q is built around the Qualcomm QCS8275 (Monaco) SoC, also marketed as Dragonwing IQ-8275. It boots from eMMC.

monaco.mk builds for it:

  • the open boot chain: TF-A and OP-TEE, which support Monaco as a SoC of its own next to Lemans, and U-Boot;
  • a Linux kernel with a Buildroot initramfs, packed in a UKI.

The quick start goes from an empty directory to a flashed board.

Boot chain

XBL -> TF-A BL2 (tz) -> BL31 -> OP-TEE -> U-Boot (uefi) -> UKI (efi): Linux at EL2
  1. XBL loads TF-A BL2 from the tz partition, and the FIP, wrapped in an ELF, from the uefi partition.
  2. BL2 loads BL31, OP-TEE (BL32) and U-Boot (BL33) from the FIP.
  3. U-Boot starts the UKI from the ESP through UEFI: bootefi bootmgr finds it as EFI/BOOT/bootaa64.efi.

The TZ stage: TF-A BL2 or U-Boot SPL

TF-A BL2 is the TZ stage by default. TZ_IMAGE=u-boot-spl makes U-Boot SPL the TZ stage instead, as on the IQ-9075 EVK. Pass the same TZ_IMAGE to bootimage, tz-qti-sign and flash-loader: 

make bootimage TZ_IMAGE=u-boot-spl     # u-boot-spl.elf, uefi.elf
make tz-qti-sign TZ_IMAGE=u-boot-spl   # tz.mbn from u-boot-spl.elf
make flash-loader TZ_IMAGE=u-boot-spl

SPL needs no storage driver. XBL loads the uefi image to 0xaf000000 before it starts the TZ stage, so SPL finds a FIT there with BL31, OP-TEE and U-Boot (monaco/uefi.its, wrapped and signed like the FIP ELF). SPL loads the three images to the addresses in the table above and starts BL31. TF-A is then built as BL31 only.

Compared with the IQ-9075 EVK:

  • SPL needs a QTI signature, like BL2: XBL checks the QTI signature of the TZ image even with secure boot disabled (see Signing).
  • SPL has to fit where XBL enters the TZ image, 0x14680000 to 0x1469a000 in system IMEM, with its BSS and stack.
  • SPL prints its banner on the debug UART that XBL leaves set up.

SPL is built from qcom_monaco_spl_defconfig in the U-Boot tree monaco.xml pins.

The board device tree (monaco-arduino-monza.dts) and the Monaco EL2 overlay (monaco-el2.dtso) are in mainline since v7.1. The kernel has no combined EL2 DTB for this board, so monaco.mk builds the board DTB with symbols and applies the overlay with the kernel's fdtoverlay.

The pinned kernel carries these patches, not submitted yet:

  • DSP (PAS) start without a resource table;
  • audio recovery across an ADSP restart;
  • fixes for booting with maxcpus;
  • L1 PM Substates disabled on the PCIe0 root port link to the PI7C9X2G304 switch, where config reads to the switch could stall a CPU;
  • the switch's Training Error masked, which made AER reset the TUSB7340 link in a loop.

monaco/patches/linux/ adds the iris video codec series: the firmware boot through the OP-TEE PAS backend (the PAS ID on suspend and resume, no SCM-only content protection call) with Linux mapping the stream the video core fetches its firmware with, as no hypervisor does at EL2, and the EL2 overlay change that enables iris with that stream. The patches are on their way upstream or in the qualcomm-linux kernel, except the one that creates the firmware stream device.

Boot CPU

XBL and TF-A enter U-Boot on CPU0, a Cortex-A78C. The Cortex-A78C cores have pointer authentication and the Cortex-A55 cores do not. Linux only brings up CPUs that match its boot CPU in that respect.

The board configuration (CONFIG_BOOT0_QCOM_BOOT_CPU) makes U-Boot start the first Cortex-A55 (MPIDR 0x10000) with PSCI CPU_ON and turn CPU0 off. U-Boot and Linux then run on a Cortex-A55, and all eight CPUs come up.

Build

make toolchains
make all                         # bl2.elf, fip.elf, efi.bin in monaco/output/
make tz-qti-sign QTI_SIGN_DIR=... CASS_CAPABILITY=... \
     QTI_SIGN_SERVER_URL=... QTI_SIGN_SERVER_PORT=...   # tz.mbn

tz-qti-sign adds the SWIV segment and signs bl2.elf with Qualcomm sectools through the QTI remote signing service. The Monaco TZ security profile comes from the Qualcomm signing package.

XBL boots only a QTI-signed TZ image, so tz.mbn has to be signed with make tz-qti-sign before flashing. Without one in monaco/output/, flash-loader uses a QTI-signed tz.mbn placed in monaco/input/ (u-boot-spl.mbn for the SPL flow). make bootimage removes monaco/output/tz.mbn, as it no longer matches the new bl2.elf.

Each make invocation stamps a build identifier, BUILD_ID (default monaco-<UTC date-time>), into the TF-A build string, the OP-TEE version, the U-Boot and Linux versions and /etc/issue, so the console shows which build is running. The build fails if an image lacks it, and monaco/output/build-info.txt records the identifier of each image.

Memory test

The kernel is built with CONFIG_MEMTEST. With memtest=<N> on its command line it writes and checks N patterns over all free memory early in the boot, before it starts the other CPUs, and reserves any range that fails. It does nothing without memtest=. 

make efi LINUX_CMDLINE="root=/dev/ram0 rw console=ttyMSM0,115200 earlycon qcom_scm.download_mode=1 memtest=4"

The kernel log then has an early_memtest: # of tests: 4 line, one line per memory range and pattern, and a bad mem addr line for each failing range; /proc/meminfo reports the size reserved as EarlyMemtestBad.

Flash

qdl writes the images by partition name. The partition table and everything else on the eMMC stay as they are. Both slots are written, so the boot chain cannot fall back to the stock images.

The firehose programmer comes from the board's stock software image and goes in monaco/input/ (or set FIREHOSE); see monaco/input/README.md. 

make flash-loader    # tz_a, tz_b <- tz.mbn; uefi_a, uefi_b <- fip.elf
make flash-kernel    # efi <- efi.bin

which run:

qdl --storage emmc prog_firehose_ddr.elf \
    write tz_a tz.mbn write tz_b tz.mbn \
    write uefi_a fip.elf write uefi_b fip.elf
qdl --storage emmc prog_firehose_ddr.elf write efi efi.bin

On a LAVA lab board

flash-lava writes what flash-loader and flash-kernel write, and flash-lava-yocto what flash-yocto writes, to a VENTUNO Q in the LAVA lab (lava.infra.foundries.io, device type monaco-arduino-monza) instead of one on USB. They package a qcomflash tarball, upload it and ask how to flash:

  • interactive (the default): reserve a board, flash it once and open its serial console; Ctrl+D closes the console and releases the board;
  • flash-only: a one-shot LAVA job that flashes the board and boots it to a login prompt.
make flash-lava                            # asks
make flash-lava-yocto FLASH_LAVA_CONNECT=0  # 1: interactive, 0: flash-only

LAVA runs qdl with rawprogram files, so flash-lava writes the five partitions at their place in the eMMC layout flash-yocto writes; a board with another layout needs flash-lava-yocto first. The interactive mode needs a board that allows the LAVA serial-console proxy. The LAVA token and the other requirements are in qcom/lava/README.md.

DSPs and audio

The rootfs carries:

  • the ADSP, CDSP and GPDSP firmware from linux-firmware (qcom/qcs8300);
  • the FastRPC userspace and runtime;
  • qcom-tests: ADSP and CDSP FastRPC, the GPDSP boot state, CPU stress, and CDSP FastRPC in an unsigned PD.

A DSP only loads the FastRPC shell and skels whose hashes its signed image carries, so the runtime has to come from the DSP build of the firmware. The build installs the QCS8300-RIDE runtime of that build under the Arduino Monza path the DT model maps to, and checks the pairing.

The DSPs are started through the OP-TEE PAS service (the Monaco PAS pseudo-TA, embedded as an early TA), which relies on the TF-A Monaco clock setup. monaco.xml pins OP-TEE and TF-A revisions with both.

The sound card, ALSA id arduinomonza (card 1; the loopback card is card 0), runs on the ADSP with the AudioReach topology from linux-firmware. Playback on the headphone output needs the route the upstream UCM profile sets: 

amixer -c arduinomonza cset name='LPI_MI2S_RX_0 Audio Mixer MultiMedia1' on
amixer -c arduinomonza cset name='Headphone Switch' on
aplay -D hw:arduinomonza,0 -f S16_LE -r 48000 -c 2 file.wav

GPU

The rootfs carries, for the Adreno 623:

  • Mesa with the freedreno driver: EGL, OpenGL ES and GBM;
  • the GMU firmware (qcom/a623_gmu.bin) and the SQE microcode (qcom/a650_sqe.fw) from linux-firmware;
  • egl-readback: renders on the GPU through the render node, without a display, reads the pixels back and checks them, then times 500 frames. It exits 0 only if the GPU drew the expected pixels.

The EL2 overlay disables the zap shader: Linux takes the GPU out of secure mode itself, with no zap shader firmware. The GPU SMMU aperture, through which the GPU switches page tables per process, is set up by TF-A BL31 at boot; without it the first draw hangs the GPU.

KVM

Linux runs at EL2, so KVM is available in VHE mode (/dev/kvm). The rootfs carries kvmtool (lkvm) and, in /opt/kvm-unit-tests, the KVM unit tests built for kvmtool with their runner: small guests that each check one part of KVM and its virtual hardware (exception vectors, SMP, GIC and ITS, timers, PSCI, PMU, debug, FPU context, micro benchmarks). 

cd /opt/kvm-unit-tests
export MAX_SMP=$(nproc) TIMEOUT=0
./run_tests.sh -v                       # the default tests
./run_tests.sh -a timer psci micro-bench  # some tests; -a includes the manual ones

BusyBox has no getconf, from which the runner takes the number of vCPUs for the SMP tests (MAX_SMP), nor a timeout with the --foreground option the run scripts use: TIMEOUT=0 runs the tests without a time limit.

The GIC has no GICv2 compatibility, so KVM offers the guests a GICv3 only and the gicv2-* tests do not apply. The Cortex-A55 and Cortex-A78C clusters have separate PMUs and kvmtool gives a VM the PMU of the CPU it starts on: run the pmu-* tests with the VM held on one cluster, in a cgroup v2 cpuset.

/opt/kvm-guest holds a small Linux guest: a 6.18 LTS kernel built for a virtual machine with a virtio console, and an initramfs with BusyBox. Its init prints a kvm-guest: ready line with the vCPU count, the kernel release and the uptime, then runs a shell on the console; poweroff -f ends the VM. 

lkvm run -k /opt/kvm-guest/Image -i /opt/kvm-guest/initramfs.cpio.gz \
    -c 2 -m 256 --console virtio --network mode=none

kvmtool reads console input only from a terminal. A script that drives the guest console runs it on a pty, with socat (in the rootfs): 

socat STDIO EXEC:./run-guest.sh,pty,setsid,ctty,stderr
