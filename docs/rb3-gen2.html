Qualcomm RB3 Gen 2

The Qualcomm Dragonwing RB3 Gen 2 development kit is built around the QCS6490 (Kodiak) SoC. It boots from UFS.

kodiak.mk builds for it:

  • the open boot chain from upstream TF-A and OP-TEE, which support Kodiak and the RB3 Gen 2, and U-Boot;
  • a Linux kernel with a Buildroot initramfs, packed in a UKI;
  • the ADSP and CDSP firmware from linux-firmware and the FastRPC userspace and DSP runtime, in the initramfs;
  • the Adreno 643 GPU firmware from linux-firmware, in the initramfs.

Boot chain

XBL -> TF-A BL2 (tz) -> BL31 -> OP-TEE -> U-Boot (uefi) -> UKI (efi): Linux at EL2
  1. XBL loads TF-A BL2 from the tz partition into pIMEM, and the FIP, wrapped in an ELF, from the uefi partition.
  2. BL2 loads BL31, OP-TEE (BL32) and U-Boot (BL33) from the FIP.
  3. U-Boot starts the UKI from the ESP through UEFI: bootefi bootmgr finds it as EFI/BOOT/bootaa64.efi.

QTISECLIB

TF-A BL31 runs its native Kodiak drivers: PSCI, CPUCP, command DB, PDC, access control, SMMU, sec_core, QTimer and watchdog. CPU idle is WFI standby only. QTISECLIB=<path> links QTISECLIB (libqtisec.a), Qualcomm's secure setup library for SC7280, which coreboot publishes in its qc_blobs repository under its own license, in their place. qtiseclib-fetch downloads release 00069 at a fixed qc_blobs commit into kodiak/blobs/ and checks its SHA-256.

DSPs

The rootfs carries the ADSP and CDSP firmware from linux-firmware, under the names the RB3 Gen 2 device tree requests:

Remote processorFirmwareVersion
ADSPqcom/qcs6490/adsp.mbnADSP.HT.5.5.c8-00246-KODIAK-1
CDSPqcom/qcs6490/cdsp.mbnCDSP.HT.2.5.c3-00130-KODIAK-1

with their protection-domain lists (*.jsn) and the terms they are distributed under, LICENSE.qcom and qcom/NOTICE.txt in /lib/firmware. dsp-firmware (a prerequisite of buildroot) fetches them from linux-firmware at a pinned revision (DSP_FW_REV) into kodiak/blobs/dsp/ and checks every staged file against kodiak/dsp-firmware.sha256. Linux starts both DSPs at boot through the OP-TEE PAS pseudo-TA. The rootfs has no audio userspace.

FastRPC: the kernel driver (QCOM_FASTRPC, with the DMA-BUF heaps its clients allocate from), the userspace from fastrpc (the adsprpcd and cdsprpcd daemons, started by /etc/init.d/S60fastrpc once the device nodes appear, and fastrpc_test), qrtr and tqftpserv. A DSP only loads the FastRPC shell and skels whose hashes its signed image carries, so the DSP runtime in /usr/share/qcom/qcm6490/Thundercomm/RB3gen2/dsp/ is the dsp-binaries runtime of the two firmware builds above (tag DSP_BIN_TAG); dsp-firmware checks the pairing with qcom/scripts/dsp-runtime-check.py and installs the conf.d entry that maps the device tree model to it. Check on the board: fastrpc_test -d 3 -U 0 (CDSP, signed PD), fastrpc_test -d 3 -U 1 (unsigned PD) and fastrpc_test -d 0 -U 0 (ADSP).

Video codec

The video core of the RB3 Gen 2 (qcom,sc7280-venus) is driven by iris, which registers a V4L2 mem2mem decoder (H.264, HEVC, VP9) and encoder (H.264, HEVC). Its firmware, qcom/vpu/vpu20_p1.mbn (VIDEO.VPU.2.0-00055-PROD-1) from linux-firmware, is in the rootfs and checked against kodiak/dsp-firmware.sha256 with the DSP firmware; iris loads it on the first open of a video node, and OP-TEE authenticates and starts it through the PAS pseudo-TA. With no hypervisor, Linux maps the firmware for the stream the video core fetches it with: the Kodiak EL2 overlay of the pinned kernel disables the video core, and patch 0004 in kodiak/patches/linux/ enables it with that stream (video-firmware).

The rootfs also carries FFmpeg and the reference streams of the video-codec test (see Video codec test). Its board facts for the RB3 Gen 2: device aa00000.video-codec, driver qcom-iris, firmware /lib/firmware/qcom/vpu/vpu20_p1.mbn, decoders h264 hevc vp9, encoders h264 hevc.

And the model of the npu-qnn test (see NPU test), which runs on the CDSP's HTP: board facts HTP_ARCH=v68, HTP_DEVICES=0:cdsp.

GPU

The msm driver brings up the Adreno 643 with its SQE microcode, qcom/a660_sqe.fw, and its GMU firmware, qcom/a660_gmu.bin, both from linux-firmware, in the rootfs and checked against kodiak/dsp-firmware.sha256. The Kodiak EL2 overlay disables the zap shader: Linux takes the GPU out of secure mode itself, so the zap shader firmware is not installed.

The rootfs carries the GPU userspace of qcom/gpu/gpu.mk (see GPU userspace): Mesa freedreno with EGL, OpenGL ES, GBM and RustiCL (OpenCL), TensorFlow Lite with XNNPACK and its GPU delegate, egl-readback, clinfo and tflite-run, for the gpu-render test and the cpu:tflite and gpu:tflite-gpu entries of the inference test.

Build

make toolchains
make all                         # bl2.elf, tz.mbn, fip.elf, efi.bin in kodiak/output/

bootimage signs bl2.elf into tz.mbn as a TZ-TEE image with the OEM TEST key of Qualcomm sectools 1.50, from the public Qualcomm Software Center (sectools-fetch checks its SHA-256), and the Kodiak security profile in kodiak/security/, as build-kodiak does; make tz-oem-sign signs again. The XBL of the QCM6490 boot binaries 00142 verifies this signature; older releases do not boot the image, so the flash targets write the boot binaries of that release with it. make tz-qti-sign QTI_SIGN_DIR=... CASS_CAPABILITY=... QTI_SIGN_SERVER_URL=... QTI_SIGN_SERVER_PORT=... replaces tz.mbn with a QTI-signed one (QTI remote signing service); kodiak/input/tz.mbn takes one signed elsewhere.

Each make invocation stamps BUILD_ID (default kodiak-<UTC date-time>) into the TF-A build string, the OP-TEE version, the U-Boot and Linux versions and /etc/issue; the build fails if an image lacks it, and kodiak/output/build-info.txt records the identifier of each image. The kernel is built with CONFIG_MEMTEST (see the VENTUNO Q page).

Flash

bootbinaries-fetch (run by the flash targets) downloads the QCM6490 boot binaries 00142 from the Qualcomm Software Center, with the immutable companion archive that carries cpucp.elf, checks their SHA-256 and unpacks them into kodiak/blobs/bootbinaries/; the UFS firehose programmer comes from there (or set FIREHOSE). The flash targets stage the images with a qdl rawprogram<LUN>.xml per LUN, at their place in the RB3 Gen 2 UFS layout (qcom-ptool qcs6490-rb3gen2/ufs); the partition tables and the other partitions stay as they are. 

make flash-loader    # xbl_a/b, xbl_config_a/b (LUN 1, LUN 2), aop, xbl_ramdump,
                     # hyp, devcfg, qupfw, uefisecapp, imagefv, shrm,
                     # multiimgoem, cpucp (A and B), toolsfv <- boot binaries;
                     # tz_a, tz_b <- tz.mbn; uefi_a, uefi_b <- fip.elf
make flash-kernel    # efi <- efi.bin

which run:

cd kodiak/output/flash-loader
qdl --storage ufs prog_firehose_ddr.elf \
    rawprogram1.xml rawprogram2.xml rawprogram4.xml patch1.xml patch2.xml patch4.xml
qdl --storage ufs prog_firehose_ddr.elf write efi efi.bin

flash-lava writes the same partitions on an RB3 Gen 2 in the LAVA lab (device type qcs6490-rb3gen2), as on the VENTUNO Q, with rawprogram0.xml, rawprogram1.xml, rawprogram2.xml and rawprogram4.xml.

KVM

Linux runs at EL2, so KVM is available in VHE mode (/dev/kvm). The rootfs carries kvmtool, the KVM unit tests in /opt/kvm-unit-tests and a small Linux guest in /opt/kvm-guest, as on the VENTUNO Q. The Cortex-A55 and Cortex-A78 clusters have separate PMUs: run the pmu-* tests with the VM held on one cluster.
