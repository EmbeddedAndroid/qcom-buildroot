Qualcomm RB3 Gen 2

The Qualcomm Dragonwing RB3 Gen 2 development kit is built around the QCS6490 (Kodiak) SoC. It boots from UFS.

kodiak.mk builds for it:

  • the open boot chain from upstream TF-A and OP-TEE, which support Kodiak and the RB3 Gen 2, and U-Boot;
  • a Linux kernel with a Buildroot initramfs, packed in a UKI.

Boot chain

XBL -> TF-A BL2 (tz) -> BL31 -> OP-TEE -> U-Boot (uefi) -> UKI (efi): Linux at EL2
  1. XBL loads TF-A BL2 from the tz partition into pIMEM, and the FIP, wrapped in an ELF, from the uefi partition.
  2. BL2 loads BL31, OP-TEE (BL32) and U-Boot (BL33) from the FIP.
  3. U-Boot starts the UKI from the ESP through UEFI: bootefi bootmgr finds it as EFI/BOOT/bootaa64.efi.

QTISECLIB

TF-A BL31 on Kodiak links QTISECLIB (libqtisec.a), Qualcomm's secure setup library for SC7280, which coreboot publishes in its qc_blobs repository under its own license. Without it TF-A builds a stub that does not boot. qtiseclib-fetch (a prerequisite of tfa) downloads release 00069 at a fixed qc_blobs commit into kodiak/blobs/ and checks its SHA-256; QTISECLIB=<path> uses another copy.

Build

make toolchains
make all                         # bl2.elf, fip.elf, efi.bin in kodiak/output/
make tz-qti-sign QTI_SIGN_DIR=... CASS_CAPABILITY=... \
     QTI_SIGN_SERVER_URL=... QTI_SIGN_SERVER_PORT=...   # tz.mbn

tz-qti-sign signs bl2.elf with Qualcomm sectools through the QTI remote signing service. The Kodiak TZ security profile (kodiak_tz_security_profile.xml in QTI_SIGN_DIR) comes from the Qualcomm signing package. XBL boots only a QTI-signed TZ image; without one in kodiak/output/, flash-loader uses a QTI-signed tz.mbn placed in kodiak/input/.

Each make invocation stamps BUILD_ID (default kodiak-<UTC date-time>) into the TF-A build string, the OP-TEE version, the U-Boot and Linux versions and /etc/issue; the build fails if an image lacks it, and kodiak/output/build-info.txt records the identifier of each image. The kernel is built with CONFIG_MEMTEST (see the VENTUNO Q page).

Flash

qdl writes the images by partition name; the partition tables and everything else on the UFS stay as they are. The UFS firehose programmer comes from the QCM6490 boot binaries and goes in kodiak/input/ (or set FIREHOSE); see kodiak/input/README.md. 

make flash-loader    # tz_a, tz_b <- tz.mbn; uefi_a, uefi_b <- fip.elf
make flash-kernel    # efi <- efi.bin

which run:

qdl --storage ufs prog_firehose_ddr.elf \
    write tz_a tz.mbn write tz_b tz.mbn \
    write uefi_a fip.elf write uefi_b fip.elf
qdl --storage ufs prog_firehose_ddr.elf write efi efi.bin

flash-lava writes the same partitions on an RB3 Gen 2 in the LAVA lab (device type qcs6490-rb3gen2), as on the VENTUNO Q: a rawprogram0.xml for LUN 0 and a rawprogram4.xml for LUN 4, at their place in the RB3 Gen 2 UFS layout (qcom-ptool qcs6490-rb3gen2/ufs).

KVM

Linux runs at EL2, so KVM is available in VHE mode (/dev/kvm). The rootfs carries kvmtool, the KVM unit tests in /opt/kvm-unit-tests and a small Linux guest in /opt/kvm-guest, as on the VENTUNO Q. The Cortex-A55 and Cortex-A78 clusters have separate PMUs: run the pmu-* tests with the VM held on one cluster.
